# Othello Constitution

## Core Principles

### I. Test-First (NON-NEGOTIABLE)
TDD が強制される：テストを最初に書き、ユーザー（このプロジェクトでは開発者＝私）が承認した後、テストが失敗するのを確認してから実装に入る。Red-Green-Refactor サイクルを厳格に守る。いかなる機能実装もテストなしには完了しない。

### II. Coverage Minimum 90%
すべての機能コードに対して、単位テスト＋統合テストによるカバレッジ率は 90% 以上が合格条件。90% 未満の状態でタスクを完了させてはいけない。カバレッジ計測には `pytest-cov`（Python）を用いる。

### III. E2E Tests Required
特徴量の主要フローは E2E テストでカバーする。スコープ：
- 石の配置～反転～勝敗判定までの典型フロー
- 回転ターンを使った戦略的展開（ボード 90°回転＋その後の反転関係の変化）
- CLI 操作（十字キー移動、エンター配置）の入力シーケンス
E2E は `pytest` ベースの統合テストとして記述し、ユニットテストと同様に CI/手動実行可能にする。

### IV. CLI Interaction Model
ゲーム操作は「十字キーでカーソル移動、エンターでコマを置く」方式のコンソール UI を基本とする（MVP での約束）。方向キーの捕捉、エンター検出、カーソル再描画等の入力処理はテスト可能なモジュールとして切り出す。

### V. Game Rules: Board Rotation Variant
- ボードは 8×8 固定（初期サイズ可変は後続機能とする）。
- 自分の通常ターンでは「石を置く」か「ボードを 90° 回転させる（時計回り）」のいずれか 1 つだけ実行できる。回転ターンでは石を置かない。
- 回転ターンは両プレイヤーとも使用可能。特定の条件制限は設けない（自由に使える）。
- ボード回転時、すべての石も盤面とともに回転する。回転によって反転関係が変化しうることをゲームの主要戦略要素とする。
- 勝敗条件は従来通り「最終的に石の多いほうの勝ち」。特殊駒・ミッション制등은 후속 기능으로 미룬다。

### VI. Playability First
実装の各段階で「実際に遊べる状態」を素早く作ることを優先する。最低限、石を置いて反転が見える・回転できる・勝敗が出る――この 3 つが動くところまでを MVP とする。遊びながら確認できるよう、実行エントリーポイントは明快にする（例: `python othello/cli.py` または `python -m othello`）。

### VII. Simplicity & YAGNI
最初から多機能にせず、ボード回転＋CLI 操作という核を突き詰める。追加ルール（特殊駒、ミッション、サイズ可変等）は別 feature として後続仕様で扱う。

## Development Workflow

### TDDサイクル
1. 仕様を読み、テストケースを考案
2. テストを記述（Red）
3. テストが失敗することを確認
4. 最小実装（Green）
5. リファクタ（重複除去・構造改善、テスト再実行で回帰確認）
6. カバレッジ確認（`pytest-cov` で 90% 以上）

### 確認フェーズ
各 feature 実装後、実際に対局して遊び、想定と異なる挙動がないか確認する。この確認結果は E2E ケースの追加やバグ修正に反映する。

### E2E 実行
`pytest`でユニットテストと E2E を一緒に走らせられるように構成する。ゲーム状態のスナップショット・入力シーケンスを再現する形で書く。

## Quality Gates

- どのタスクも対応するテスト無しには完了と見なさない。
- カバレッジ 90% 以上に達しない場合、追加テストまたは実装の見直しを行う。
- E2E で主要フローが通らない場合、ユニットレベルに遡って原因を究明する。
- コードレビュー（自己レビュー含む）でテストの妥当性・カバレッジ・E2E の網羅性を確認する。

## Governance

憲法は本プロジェクトのあらゆる実装判断に基本的な指針を与える。 Amendments は仕様・実装と同様、テストで裏付けられた変更として記録する。原則間の秩序が競合する場合は、上位の原則（Test-First, Coverage Minimum, E2E Required）が優先する。
